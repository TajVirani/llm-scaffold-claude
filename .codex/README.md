# Codex shim

The Codex CLI side of the workflow 2.0 scaffold (D9, D40, D66, D67). The only other host is Claude Code, so there are no Cursor, Gemini or Copilot shims. Everything here was checked against `codex-cli 0.155.1` (`PLAN/hook-verification-codex.md`). This file describes what `install.sh` creates in a target project. The scaffold repo itself ships no `.codex/hooks.json` or `.codex/config.toml`.

## What install.sh creates in `<target>/.codex/`

| File | Source | Notes |
|---|---|---|
| `agents/<codex-name>.toml` | `.agents/hooks/generate-codex-agents.sh` run on `.agents/agents/*.md` | Exactly the keys `name`, `description` and `developer_instructions` (the definition body). `<codex-name>` is the definition name with `-` mapped to `_` (see Agent names below). It never writes `model` (D67). Re-run on every install or upgrade; `--check` reports drift. Stale generated files are pruned, and user-written tomls (no `# Generated by` marker) are left alone |
| `hooks.json` | `.agents/hooks/codex-hooks.template.json` | Hook wiring, see below |
| `config.toml` | `.agents/hooks/codex-config.template.toml` | Permissions profile `workflow` for the hard write limits |

Nothing else is needed:

- **Project instructions.** Codex reads `AGENTS.md` natively, from the root down to the cwd, with a 32 KiB default cap. It does not read `CLAUDE.md`.
- **Skills.** Codex finds `.agents/skills/*/SKILL.md` natively, including symlinked folders (verified, row 1). Skill frontmatter needs `name` and `description`. `agents/openai.yaml` is optional.
- **Workflow commands.** Codex custom prompts are deprecated and user-level only, so the workflow ships to Codex as skills (D27). There is no output-style equivalent.

After install, and again after every upgrade, the user must trust the project `.codex/` layer and review the hooks with `/hooks`. Codex pins trust to the hook hash. `--dangerously-bypass-hook-trust` is for automation only.

## Hooks (`codex-hooks.template.json`)

| Event | Matcher | Script | Timeout | Why |
|---|---|---|---|---|
| `SessionStart` | (none) | `session-start-resume.sh` | 10 | Resume offer, through `additionalContext` |
| `PreToolUse` | `Bash` | `block-destructive-git.sh` | 10 | It reads `tool_input.command`, which Codex's `Bash` payload has. Deny JSON is the same as Claude's |
| `PreToolUse` | `apply_patch` | `codex-write-guard.sh` | 30 | The three write guards for Codex. It splits the patch text in `tool_input.command` into its `Add`/`Update`/`Delete`/`Move to` paths and runs `check-write.sh --only spec`, `--only tier-a` and `--only tier-b` on each, with `--agent` when the payload has `agent_id`. Any denied path denies the whole patch, and deny wins (row 5b). It fails closed on a patch it cannot parse. For `specs/*/spec.md` an `Add` passes its content as `--proposed`; an `Update` is denied when its `-`/`+` lines change a top-level `status:` or `blocked_condition:` |
| `PreToolUse` | `.*spawn_agent` | `codex-pre-spawn.sh` | 30 | Spawn validation on the plaintext fields (the `message` is encrypted). For a workflow `agent_type` (definition or Codex name) it checks the `task_name` form (below), that `s<NNN>` resolves to exactly one `specs/<NNN>-*`, and that an encoded work type matches exactly one `profiles/<wt>.md`. Other agents pass through |
| `PostToolUse` | `Bash` | `evidence-capture.sh` | 60 | Browser-suite evidence. On Codex `tool_response` is a plain string with no exit code (row 6) |
| `PostToolUse` | `apply_patch` | `codex-rules-sync.sh` | 60 | When the patch adds, updates or moves to a `docs/rules.md`, it hands `rules-boundary-config-sync.sh` an equivalent `Write` payload, so `tools/boundaries/` is regenerated (block with reason when rules.md does not parse) |
| `SubagentStop` | (none) | `post-implementation-audit.sh` | 600 | Toolchain audit. It finds the task from the spawn `task_name` (see below). The script filters on `agent_type`. Block-with-reason and `stop_hook_active` are verified (rows 4c, 4d) |

- **Matchers** are full-match regexes on the hook-side tool name. The verified names are `Bash`, `apply_patch` and `.*spawn_agent` (the spawn tool reports as `collaborationspawn_agent`). `spawn_agent`, `^Agent$` and `Agent` do not fire (row 3a).
- **Command form.** Each command is `bash -c 'exec "$(git rev-parse --show-toplevel 2>/dev/null || pwd)/.agents/hooks/<script>"'`. Codex sets no project-dir variable (row 8) and runs hooks with `pwd` set to the session cwd, which can be a sub-directory. The form works whether Codex runs the command through a shell or splits it into argv (both are tested in `tests/hooks/codex-shim.sh`). Scripts take every path from the payload `cwd`.
- **Timeouts.** These use the Claude template's values. The Codex handler has a `timeout` key, but its unit was not checked live (seconds assumed).

- **Patch parsing** (`_codex-patch.sh`, shared by the write guard and the rules sync). It accepts the Codex patch format: an optional heredoc wrapper line, `*** Begin Patch`, file sections, `*** End Patch`. `*** Move to:` must follow its `*** Update File:` line directly. An unknown `*** ` line, an empty path, text before `Begin` or after `End`, or a patch that names no file is a parse error, and the write guard then denies. `tool_input.command` may also be an argv array; the last element is the patch.

## Task lookup for the stop audit (D66)

- **Verified.** The SubagentStop payload has no `task_name`, but `agent_transcript_path` does. The first line of a Codex sub-agent rollout is a `session_meta` record. Its `payload.agent_path` is `/root/<task_name>`, with the same value under `payload.source.subagent.thread_spawn.agent_path`, and `agent_role` is the agent type. This was checked against the six sub-agent rollouts from the 0.155.1 verification runs: each `agent_path` equals the spawn `task_name` that PostToolUse returned, for example `probe_agent` → `/root/probe_agent`. A nested spawn gets `/root/<parent>/<name>`, and the hook uses the last segment.
- **Name rules.** Codex 0.155.1 accepts only lowercase letters, digits and underscores in a `task_name`, and no `/`. This comes from the binary's validation strings ("agent_name must use only lowercase letters, digits, and underscores", "agent_name must not contain `/`") and was not exercised live. So the earlier forms `<NNN-slug>/<T-id>`, `<NNN-slug>/integration-<wt>` and `<NNN-slug>/phase-1-<wt>` cannot be used. The orchestrator must encode them:

  | Launch | `task_name` | Example |
  |---|---|---|
  | Task (3.3) | `s<NNN>_t<N>` | `specs/007-checkout`, `T3` → `s007_t3` |
  | Phase 1 (1.2, 1.3) | `s<NNN>_phase_1_<enc(work_type)>` | `s007_phase_1_test_harness` |
  | Integration batch (3.2) | `s<NNN>_integration_<enc(work_type)>` | `s007_integration_web` |
  | Mini-review (3.7) | `s<NNN>_t<N>_r<round>` (required; the bare `s<NNN>_t<N>` is the implementer's name) | `s007_t3_r1`, `s007_t3_r2` |
  | Repeated Phase 0/4 launch | `s<NNN>_<enc(task_type)>_r<round>` (the name is optional, but when one is given, `_r<round>` is required on every launch of a type that runs more than once per spec, so each spawn gets a new name) | `s007_fact_lookup_r2` |

  `enc` lowercases and turns every character outside `[a-z0-9]` into `_`. The hook resolves `s<NNN>` to the single folder `specs/<NNN>-*`, and the Phase 1 work type to the single `profiles/<wt>.md` whose encoded name matches. Zero or several matches, or any other name, allows the stop with a warning (D55). `codex-pre-spawn.sh` applies the same resolution before the spawn and denies instead: a missing or malformed `task_name` for `implementation`, `integration` or `profile-mini-review`, or an `s<NNN>` / work type that does not resolve to exactly one folder or profile. For other workflow types the `task_name` is optional; one that starts with `s<NNN>_` must resolve to one spec folder.
- **Worktree.** Codex has no `isolation` option and its sub-agents run in the main checkout, so the orchestrator creates each implementation and integration worktree itself: `git worktree add .worktrees/<task_name> -b wf/<NNN-slug>/<task_name>` (`.worktrees/` gitignored), and names it in the brief as the directory the agent works in. The stop audit runs the toolchain in `<main checkout>/.worktrees/<task_name>` and still writes evidence under the main checkout's `specs/<NNN-slug>/artifacts/`. When that directory is missing, it allows the stop with a warning (D55) instead of auditing the main checkout.

## Agent names

- Codex 0.155.1 accepts only `[a-z0-9_]` in an `agent_name` (`task_name`). Whether an agent definition `name` with a hyphen (`fact-lookup`, `profile-mini-review`) loads is **not verified**. To be safe, `generate-codex-agents.sh` writes `<codex-name>.toml` with `name = "<codex-name>"`, where `<codex-name>` is the definition name with every `-` mapped to `_`: `fact-lookup` → `fact_lookup`, `profile-mini-review` → `profile_mini_review`, `cache-regeneration` → `cache_regeneration`. Two definitions that map to the same name are an input error. Generated files under the old hyphenated names are pruned on the next run.
- So on Codex, spawn with `agent_type: <codex-name>`. `resolve-launch.sh --task-type` keeps the definition name (`fact-lookup`). `codex-pre-spawn.sh` accepts both forms. `post-implementation-audit.sh` filters on `implementation`, which has no hyphen.

## Hard write limits (`codex-config.template.toml`)

- The `workflow` profile has `extends = ":workspace"` plus `"docs/cache" = "read"`. It blocks both `apply_patch` and sandboxed shell writes (rows 7a, 7b; re-checked with `codex sandbox -P workflow`). Without `extends`, every sandboxed shell aborts with exit 134 (row 7c).
- **`specs/*/.step` cannot be listed (G7 resolved).** 0.155.1 rejects the profile with "filesystem glob path `specs/*/.step` only supports `deny` access". `deny` also blocks reads, which the workflow scripts need. So `.step` stays guarded by `check-write.sh` only.
- **Side effect.** Commands the agent runs inside the sandbox cannot write `docs/cache` either. `publish-cache.sh` (regenerate-caches) therefore needs an approved escalation, with an approval policy that can ask (the default `on-request`), or a run outside Codex.
- The Codex docs say `:workspace` keeps `.git`, `.agents` and `.codex` read-only. Under `codex sandbox -P workflow` all three were writable, so the scaffold does not rely on that.

## Models (D35, D67)

- A toml `model` overrides the spawn-time model, even one set through `updatedInput` (row 2c). So the generated tomls never carry `model`. The orchestrator passes the model that `resolve-launch.sh --host codex` resolves (`agent-overrides.yaml` > definition `models.codex` > `model-map/`) as the spawn `model`. That works when the toml has no `model` (row 3c).
- **Caveat.** The 0.155.1 multi-agent prompt says that full-history forks (`fork_turns` omitted or `"all"`) "inherit the parent model and reasoning effort and do not accept overrides". Run 3 still applied a model on a `fork_turns:"all"` spawn. To be safe, the orchestrator should spawn with `fork_turns: "none"`, which also keeps the parent's history out of the sub-agent.
- G8 closed: the tier defaults are `gpt-6-luna` (cheap) and `gpt-6-sol` (strong), from the 0.155.1 model list (D23). They are model names, not aliases, and get retired, so `project-setup` checks them against `codex debug models` when Codex is in use.

## Merge rules for `install.sh` (D11)

- `agents/`: run `generate-codex-agents.sh` after `.agents/` is copied.
- `hooks.json`: if absent, write the template. If present, append the template's matcher groups per event, and skip a group whose `command` is already there, so reinstalling is idempotent.
- `config.toml`: if absent, write the template. If present, add the `[permissions.workflow]` tables when missing. Set `default_permissions = "workflow"` only when the key is absent. Otherwise keep the user's value and warn, or overwrite with `--force`.
- Run `install.sh` outside a Codex session.
