# T09: The large-path module and its entry points

Index: [../tasks.md](../tasks.md) · Blocked by: None (can start immediately) · Parallel with: None

**What to build:** The large path as a module an agent runs, and the places the rest of the workflow hands over to it. `modules/large-path.md` is the planning route for one initiative: its entry (a clean working tree, switch to `initiative/NNN-slug`, fetching when the branch exists only on the remote), the conversion of a draft spec into an initiative, exploration in rounds over `questions.md` (compute the frontier, launch `research` and `fact-lookup` agents, ask one round, log it; a research launch may stay pending across sessions and is written back on resume), emission of a settled slice as a spec seeded through discovery 0.1, the `planned` merge into main through the generic PR mode or a local `--no-ff` merge per `task_review`, reopen, and the lazy `done` flip on resume once every emitted spec is `done` on main. Every step is numbered `6.<n>` in run order with a title; the module says which steps write `initiative.md` and which are term gates, and commits the initiative folder at each commit point. The router offers and routes initiatives, the questioning loop asks the conversion question and checks "one feature?" at 0.3.19, discovery seeds a spec from a slice and counts initiative origins and slices when numbering, deferred-handoff re-points shelf items at conversion, and sign-off flips the initiative at 5.7.

**Seam:** Prose, checked three ways: `tests/lint/step-list.sh` (every `6.x` id and the conversion node id the skill text names must exist in `steps.tsv` once T2 lands), the Phase 4 review lenses reading the module against the JRN-001, JRN-003 and JRN-005 replays in the suites, and `profile-mini-review` against the agent-docs checklist.

**Acceptance criteria:**

- [ ] `modules/large-path.md` numbers its steps `6.1`, `6.2`, ... in run order, each with a title fit for `steps.tsv`, and a table marking the writer steps (those that write `initiative.md`) and the term-gate steps; `6.1` is the entry step and writes `initiative.md` at conversion, matching `tests/fixtures/initiative.sh`.
- [ ] Conversion (from 0.3.19 "one feature? No", at the conversion node the module names in phase 0): creates `.workflow/initiatives/NNN-slug/` with the next initiative number, `initiative.md` (`status: exploring`, `origin`, `created`, `branch`, `merge_pr: null`, empty `slices`), `questions.md`, moves the spec's `design-log.md` and `codebase-map.md` in, appends an Origin entry naming the spec and an entry in the moved log re-pointing its `Spec:` line, re-points `superseded_by` and `origin_spec` on shelf items and `promoted_to` on a work item, deletes the spec folder, creates `initiative/NNN-slug` off `origin/<main_branch>` (else local) after a fetch, switches to it and commits only `.workflow/initiatives/NNN-slug/**`; every status, step, slice and question write goes through `initiative-transition.sh` with the typed repo-relative prefix.
- [ ] Rounds: the frontier is every `open` question whose `depends_on` are all `settled` (questions) or `done` on main (specs, read with `git show`); `research` questions launch with a header carrying `spec_dir` as the initiative folder and are set `researching` with `launched`; a resumed session writes the answer back as the settled line or resets to `open`; one round asks the decision questions together in the questioning loop's format; each round is logged with the Initiative round shape and committed; term gates write the glossary only at the marked steps.
- [ ] Emission: with every question of a slice settled and the stakeholder's confirmation, the initiative commit lands first, then discovery 0.1 runs seeded from the slice (the spec's Why from the slice, `initiative:` in its frontmatter, an Origin entry carrying the binding decisions), `set-slice --status emitted --spec` records it, and the session stays in the initiative unless an open question depends on the new spec; the emitted spec folder is never added to an initiative commit.
- [ ] Planned and done: `status planned` when every slice is emitted and no question is open; under `pr` or `pr-blocking` the branch is pushed and the PR/MR opened through `open-task-pr.sh --head initiative/NNN-slug --base <main_branch> --title ... --record`, waiting for approval under `pr-blocking`; under `local` a `--no-ff` merge into main; the local branch is deleted after the merge; reopen and the `done` flip re-create it off a fetched main; a resumed `planned` initiative whose emitted specs are all `done` on main (read from the main branch, never the working tree) is set `done` and merged the same way.
- [ ] `SKILL.md`: the frontmatter modules list names `large-path`, Find the state gains the branch for a request that names an initiative or picks one from the resume offer, the § 6 table has the module's row with its nodes, and the Launch header section names `research` and the `i<NNN>_<type>` Codex task name.
- [ ] `modules/questioning-loop.md`: conversion is proposed as a frontier question at any round when the design tree shows several features, and 0.3.19 checks "one feature?" before writing `spec.md`, converting at the conversion node when the answer is no.
- [ ] `modules/discovery.md`: 0.1 can be seeded from a slice (as from a work item), and 0.1.1's next-number rule counts spec folders, `refs/heads/spec/*`, `refs/remotes/origin/spec/*`, every initiative's `slices[].spec` and every initiative's `origin`, in the working tree or on an initiative branch.
- [ ] `modules/deferred-handoff.md`: a shelf item's `origin_spec` or `superseded_by` may name an initiative folder, written at conversion; `modules/sign-off.md`: 5.7 for a spec carrying `initiative:` flips the initiative to `done` through `initiative-transition.sh` once every emitted spec is `done`, and merges that change into main as `planned` was merged.
- [ ] Every path is built from `workflow-paths.sh` names in prose as the other modules do (`.workflow/initiatives/NNN-slug` written as the folder, scripts called with the full `.agents/skills/feature-workflow/scripts/` prefix); the module follows `writing-for-agents` and the agent-docs profile; no decision id appears in the text.
