Wayfinder vs the workflow 2.0 scaffold

For engineers who already use Matt Pocock's skills and want to know what this repo adds, what it costs, and when to reach for each.

The comparison is uneven by design. Wayfinder is one skill, and it only plans. It charts a map of decision tickets on your tracker and resolves them one session at a time. It never builds. This scaffold is a whole delivery system: discovery, test setup, task breakdown, implementation, review and sign-off.

So the fair comparisons are:

  • (a) Wayfinder vs the scaffold's Phase 0 (discovery and the questioning loop).
  • (b) The full Pocock pipeline vs the scaffold's end-to-end feature-workflow.
wayfinder→ to-spec→ to-tickets→ implement / implement-spec→ code-review
0 Discovery→ 1 Verification setup→ 2 Task breakdown→ 3 Implementation waves→ 4 Review + triage→ 5 Sign-off

Shared lineage. This scaffold borrows heavily from Pocock. upstream-lineage.json has 60 entries derived from mattpocock/skills. Three of them come from Wayfinder itself: the HITL/AFK tag on deferred items, and the "index, not store" shape of design-log.md. The grilling frontier, tracer-bullet tickets, worktree-per-implementer waves, two-axis review and the glossary/ADR format all trace back to Pocock too. Much of what you know carries over.

Caveat. Wayfinder's internals were summarised from skills/engineering/wayfinder/SKILL.md and docs/engineering/wayfinder.md, not read verbatim. Exact ticket templates and label handling are unverified. Scaffold claims come from this repo at commit 4c827f9.

1. TL;DR verdict

  • Unclear route over many sessions? Use Wayfinder. Its map lives on the tracker, survives across sessions and people, and keeps fog and out-of-scope items explicit. The scaffold's questioning loop assumes the route can be settled inside one feature's discovery.
  • Shipping one well-scoped feature to a standard? Use the scaffold. It enforces things the Pocock skills only ask for in prose. Hooks gate writes, the toolchain must pass before an implementer can stop, test suites are proven red before code is written, and three review lenses run with triage.
  • Small changes and quick adoption: Pocock wins. You can install the skills and use one today. The scaffold needs install.sh, project-setup and a standards interview, and even its light path is about 67 steps.
  • Maturity: Pocock wins clearly. mattpocock/skills is widely used, versioned with changesets and supports five or more hosts. The scaffold has a real offline test suite, but feature-workflow has never been run end to end.
  • They compose. Use Wayfinder to clear the route, then hand each decided destination to the scaffold as a spec.

5. When to use each

Migrating auth across a legacy monolith

Wayfinder

The route is unknown. You need research tickets, a prototype or two, and decisions spread over weeks. Chart the map first. Each slice that becomes clear can then go through the scaffold as its own spec.

Adding CSV export to an existing TS app

Scaffold, full path

The scope is clear and lives in one module. The scaffold's TS profile (Vitest, Playwright, oxlint, dependency-cruiser) fits directly. You get a journey test, gated tasks and a report proving it works.

One-file bug fix

Neither workflow

Use the scaffold's trivial-edit bypass if you will review it yourself, or Pocock's diagnosing-bugs / tdd on their own. Neither pipeline is worth the overhead here.

Greenfield project, conventions must stick

Scaffold

Run project-setup + project-standards. Folder layout, naming, approved libraries and import boundaries become lint config and hooks, not hopes.

Cross-team decision needing tracker visibility

Wayfinder

Stakeholders outside the repo can follow, comment on and claim tickets. A scaffold design-log.md on a spec branch is invisible to them.

Changing many independent modules in parallel

Depends

If the slices touch shared core, the scaffold's integration agent and overlap checks prevent merge fights. If they are truly independent, implement-spec is lighter.

Worked example: the minimal Splitwise app in testprompt.md

The brief: a Go backend (standard library), a React frontend, groups and members, expenses, balances, a minimal-payments "settle up" view, and data that persists across restarts.

With Wayfinder + Pocock

  • Wayfinder is probably overkill. The route is clear enough for one grilling session (storage choice, split rules, rounding, the settle-up algorithm).
  • grill-with-docs → to-spec → to-tickets (tracer bullets: create group → add expense → balances → settle up).
  • implement-spec with TDD per ticket, then code-review.
  • Fast to start, and works with Go out of the box because nothing is stack-specific.

With this scaffold

  • project-setup must define new work types first. The example profiles assume TS, Vitest, Playwright and oxlint, and the deps skills are bun-only. A Go backend needs a new profile (go test, go vet, staticcheck or golangci-lint, and a boundary tool other than dependency-cruiser).
  • The questioning loop settles rounding, money representation and the settle-up algorithm. verification-plan.md defines journeys such as "add 3 expenses → settle up shows ≤ n−1 payments".
  • Phase 1 proves the Go tests and Playwright suite fail first. Phase 3 can run backend and frontend tasks in parallel waves.
  • More upfront cost, but you get stronger evidence that "persists across restarts" and "fewest payments" actually hold.

6. Using them together

  • Wayfinder upstream, scaffold downstream. Once a map is cleared, each decided slice becomes a scaffold spec. Paste the map's Decisions into the Why and constraints at 0.1, and the questioning loop starts with a near-empty frontier.
  • Scaffold deferred shelf → Wayfinder. Items in .workflow/deferred/ that grow large or unclear can seed a Wayfinder map. Their HITL/AFK tags already match Wayfinder's ticket modes.
  • Keep one owner for glossary and ADRs. Both write GLOSSARY.md and ADRs, but in different places (docs/adr vs .workflow/decisions/adr). Pick the scaffold's location, or terms will drift.
  • Don't install both grill-me and the scaffold in one project without care. "Grill me" is routed to the scaffold's questioning loop, so the two will compete for the trigger.

7. Risks and gaps

Scaffold

  • Heavy ceremony: 89 steps on the full path, 67 on the light path. Easy to over-apply.
  • feature-workflow has never been run end to end, light or full. Phase 2→3 (branches, worktrees, waves, PRs) is also untested live.
  • Codex support is partly unverified: hyphenated agent names, the status line, and the live hook run.
  • TS/bun bias in the example profiles and the deps skills.
  • Setup prerequisites: bash, git, jq, mikefarah yq v4, and node/dependency-cruiser in targets.
  • One orchestrator per spec, and no tracker visibility for the planning stage.
  • Loose ends, for example the context-bridge file has no consumer.

Wayfinder

  • Most-reported failure: agents write production code inside a map session.
  • Large maps drift into waterfall planning unless the destination is bounded and you prototype early.
  • Parallel tickets can give conflicting answers because sessions share no context.
  • Grilling questions can be verbose. Agents may design around a wrong decision instead of challenging it.
  • No enforcement: everything relies on the agent following prose.
  • Depends on the tracker (or local .scratch/). Tracker noise and label hygiene become your problem.
