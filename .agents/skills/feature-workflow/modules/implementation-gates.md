# Per-task gates (3.4-3.8)

The [wave loop](implementation-waves.md) loads this step file when the first implementation agent of a wave returns; every returned task then passes through it. Every command runs in the spec checkout, as the wave loop says. A task that passes 3.8 waits for the wave loop's [3.16 merge](implementation-waves.md#316-merge-the-wave).

For each returned implementation, check the `implementation.yaml` the agent wrote ([Reading a result file](implementation-waves.md#evidence-and-the-ledger)): `.agents/skills/feature-workflow/scripts/check-task-result.sh .workflow/specs/NNN-slug/artifacts/<task-id>/implementation.yaml`. Then:

1. **Route the result `status`.** `done` continues below. `discovered-work` goes to [Discovered work](implementation-waves.md#discovered-work-0021). `profile-wrong`, `scope-expansion` and `blocked` go to [Stops](implementation-waves.md#stops). Separately, a non-empty `discovered_work[]` goes to [Discovered work](implementation-waves.md#discovered-work-0021) whatever the status, `done` included (a `can-wait` item may accompany a finished task); a `done` task keeps going through its gates while that module handles it.
2. **3.4 Negative and edge cases.** `tests_added` includes `negative` or `edge` tests, or the summary says why none apply. Otherwise resume the agent to add them.
3. **3.5-3.6 Tool audit clean?** On Claude the stop audit has already run the profile toolchain with `--reuse` (the command keys `lint`, `typecheck`, `format`, `boundary` and `test`; never `serve` or `serve_ready`) and blocked the agent's stop until it passed. `toolchain.json` records `tree`, the hash of the checkout's content without the workflow data folders and the Tier A files no test reads (`capabilities.md`, `review-lessons.md`, `GLOSSARY.md`, `decisions/`, `model-map.yaml`); `rules.md` and the profiles stay in, so an edit to them runs the commands again. When the agent's own 3.5 run passed on the same tree with the same commands, the audit runs nothing: it copies that record and adds `reused_from`, the evidence dir it came from. A reused pass is a pass. Read `artifacts/<task-id>/`:
   - `toolchain.json` says `pass` and there is no `audit.json`: **clean**.
   - `audit.json` with outcome `gave-up`: the agent stopped on the same failure three times. **Not clean**: a fix round with `toolchain-digest.txt`.
   - `audit.json` with outcome `warning` (or a new line in `artifacts/audit-warnings.jsonl`): the audit could not run. Run it yourself: `.agents/skills/feature-workflow/scripts/run-toolchain.sh --spec-dir .workflow/specs/NNN-slug --task-id T3 --cwd <worktree> --reuse`. Exit 0 is clean; exit 1 is a fix round with its digest; exit 2 is a header or profile problem the agent cannot fix: relaunch with a corrected header, or treat a profile problem as `profile-wrong`. One profile problem you fix on the spot: an exit 2 that says a Toolchain key "is still a placeholder" names the profile file and the key whose value starts with `TODO:`. Ask the stakeholder for that key's command (or `""` when it does not apply), write it into the profile and change nothing outside its Toolchain section (the guard allows only that at 3.3-3.5), then run the toolchain again.
   - On Codex the stop audit works the same way, finding the task from the spawn `task_name`. A malformed `task_name` makes it warn, so handle it as the `warning` case above.

   The audit's `test` key judges this task's own tests: tests other tasks will make green are still red on the spec branch by design and never fail this task's gate.
   The scoping comes from the records and the worktree: each record's `tests` lists the Phase 1 tests that task turns green (assigned at 2.5), and in an agent worktree `run-toolchain.sh` also lists the files changed since the task branch left the spec branch. It runs the profile's `test_scoped` command whenever the task's own list, the excluded set (the `tests` of every other task not yet `done`) or that changed set is present, with the task's own in `$WF_TASK_TESTS`, the excluded in `$WF_EXCLUDE_TESTS` and the changed files in `$WF_CHANGED_FILES`, so the run is the task's own suites plus the suites that cover its changed files, never the whole harness; a changed file no suite covers runs nothing for it. Only in the spec checkout with nothing listed does `test` run whole. The `test` result in `toolchain.json` records `own`, `excluded`, `changed` (the counts) and `scoped: true` whenever `test_scoped` ran. The full harness, and with it regressions outside those suites, is the 3.9 gate's job. A profile without `test_scoped` cannot be scoped: a failing `test` is then reported as `unscoped` with a warning in `toolchain.json` and does not block, so check that output yourself and add `test_scoped` to the profile.

   No agent looks at the diff until this is clean.
4. **3.7 Mini-review.** Launch `profile-mini-review` (header `spec_dir`, `task_id`, `work_type`). Hand over the diff as the task worktree path and the base commit (`yq '.base_commit'` on `implementation.yaml`; the reviewer runs `git -C <worktree> diff <base_commit>...HEAD`), plus `.workflow/specs/NNN-slug/artifacts/<task-id>/toolchain.json`; no diff file is written. Every launch is a full review, after a fix round too. When it returns, check the `mini-review.yaml` it wrote: `.agents/skills/feature-workflow/scripts/check-task-result.sh .workflow/specs/NNN-slug/artifacts/<task-id>/mini-review.yaml`. Each item is a number (the profile checklist's position, or `R1`-`R5` for the readable-code lines), a verdict, a location and, for `fail` and `tool-covered`, a one-line note; a failing `R` item also carries `fixes`, printed as one `fix` row per breach under its item row; `tool-covered` items and `fail` notes ending `(rule candidate)` feed the 5.2 proposals. A non-empty `out_of_scope_noticed` never changes the verdict: hand each entry to [Discovered work](implementation-waves.md#discovered-work-0021) with origin node `3.7`, as for `discovered_work[]`. An entry it returns as **current work** (a proven problem on lines or files this task changes, usually marked `blocks-this-task`) joins this task's 3.8 fix list as one more item, `oos <evidence location>: <summary>`, so the task gets a fix round even when the verdict is `pass`; the mini-review's `not_checked` lines go nowhere.
5. **3.8 Mini-review passes?** The fix list is the failed items (`n`, `location`, `note`: the checker's `fail` rows) plus any `oos` items 3.7 added. A non-empty fix list is routed below: a patch you apply yourself, or a fix round. An empty one (`verdict: pass` and no `oos` item) means the task is ready to merge at 3.16.

**Fix rounds.** A fix round hands the implementer the failing gate's output, followed by the gates again from 3.5 (the stop audit fires on its next stop). 3.6, 3.8, 3.9 and 3.11 failures all count. For a 3.8 fix list, what must change decides who fixes it. An `oos` item is judged like a failed item.

A **patchable item** is a failing readable-code item (`R1`-`R5`), whose `fixes` give each edit exactly, or a checklist item that fails on wording only (a comment, doc text or a name in prose; the code behaves the same once it is fixed), whose note gives the text. A readable-code breach never costs a launch: you apply it yourself, also when the list holds other items.

- **Patch.** Every item on the fix list is patchable. This is not a fix round: no agent is launched and no review runs again. Apply it yourself and the task goes on to 3.16:
  1. Rename `mini-review.yaml` to `mini-review-r<k>.yaml` ([keep earlier rounds](implementation-waves.md#evidence-and-the-ledger)).
  2. In the task worktree, make each edit as its `fix` or note gives it, and nothing else: `delete` removes the comment, `replace:` and `insert:` (above the location) write the text as given, and `rename <old> to <new>` changes the name at every listed location. For a rename, also search the task's changed files for the old name (`git -C <worktree> diff --name-only <base_commit>...HEAD`) and change any use the list missed. When a wording note leaves the text open, write it yourself from the note's reason.
  3. Run the toolchain, since no stop audit fires for your edit: `.agents/skills/feature-workflow/scripts/run-toolchain.sh --spec-dir .workflow/specs/NNN-slug --task-id <task-id> --cwd <worktree> --reuse`. With `--reuse`, `test` is not run when only comments and docs changed since the task's passing run; a rename is a code change, so `test` runs too. Exit 1: fix the text or the missed use until it exits 0. A failure you cannot fix that way (the rename collides with another name, a test needs to change) moves that item to a behaviour fix: undo its edit (`git -C <worktree> checkout -- <file>`) and continue with the rest.
  4. Commit in the worktree with a Conventional Commit subject and the task id in the body, one body line per applied fix (`git -C <worktree> commit -am "refactor: <the names and comments fixed>" -m "<task-id>: fixes from the 3.7 mini-review" -m "<n> <location>: <fix>"`; `docs:` when only comments and docs changed). Set the new commit as `head_commit` in `implementation.yaml` (`yq -i '.head_commit = "<new sha>"'`), so the record names the task branch's tip and the 3.16 merge takes the branch with the patch on it. Record what you applied in the review file, under the name it has now: `yq -i '.patched = "<new sha>"' <that file>`; the commit body lists each fix.
- **Behaviour fix.** Any item on the fix list needs the code to change and is not patchable (a rename a checklist item asks for included): first apply the patchable items yourself, as steps 2 to 4 of Patch say (the rename in step 1 waits). Then rename `mini-review.yaml` to `mini-review-r<k>.yaml` and `implementation.yaml` to `implementation-r<k>.yaml` (each name counts its own `k`), launch a fresh agent with the same header, and add to the brief "first merge branch `<branch>` into yours, then fix: <the fix list>", one line per item that is left, `<n> <location>: <note>` (an `oos` item as 3.7 wrote it). Its profile is already in its prompt, so the number names the checklist line. Its next mini-review is a full one.
 Five rounds per task at most; at the cap, go to [Stops](implementation-waves.md#stops).
