# claude-settings.template.json

The Claude Code settings fragment that `install.sh` merges into `<target>/.claude/settings.json` (D36). It holds the hook wiring, the permission deny rules for hard write limits, the output style and the status line. JSON allows no comments, so the rationale lives here. The scaffold repo's own `.claude/settings.json` carries the same wiring, because the repo runs its own workflow on itself (D36).

The matcher itself was not live-tested on 2.1.300; the verification harness registered `SubagentStop` without one.

The `:-.` fallback covers a status line run without `CLAUDE_PROJECT_DIR` set; the command then resolves from the session cwd. Needs `node` on `PATH`.

What the docs say ([permissions](https://code.claude.com/docs/en/permissions), "Read and Edit"; [sandboxing](https://code.claude.com/docs/en/sandboxing), "Permission rules"):

- Path rules are checked only for `Edit(...)` and `Read(...)`. A `Write(path)` or `NotebookEdit(path)` rule is accepted but never consulted. `Edit` rules apply to all built-in tools that edit files, so one `Edit` rule covers Write, Edit and NotebookEdit.
- Patterns are gitignore-style. A relative single-segment directory pattern such as `.workflow/**` matches at any depth under the cwd when used as a deny rule. That depth also covers worktree copies under `.claude/worktrees/` (D18).
- Edit deny rules also cover file commands Claude Code recognizes in Bash (`sed`, `tee`, ...) and redirect targets (`> file`). They do not cover arbitrary subprocesses that write files themselves, such as a script.
- Deny rules are evaluated first, in every scope, whatever a PreToolUse hook returns.
- In a `Bash(...)` rule, `*` matches any text at any position, spaces included. A Bash rule is text matching on the command line, not a security boundary.

**Gap (sandbox).** The sandbox is off by default. When it is on, `Read` and `Edit` deny rules are merged into the sandbox configuration, which is enforced at the OS level on every Bash command and its children. A target project that enables the sandbox would therefore block `status-transition.sh`'s write of `.workflow/specs/*/.step` and `initiative-transition.sh`'s write of `.workflow/initiatives/*/.step`. That project must run both scripts outside the sandbox, with exact `sandbox.excludedCommands` entries for the command lines the `feature-workflow` skill uses. `excludedCommands` matches the call text, so the skill must call each script the same way every time. For the same reason the template adds no `sandbox.filesystem.denyWrite`. Tier A and `spec.md` have no hard limit: a Bash write that bypasses the guards is caught only at review.

## Merge rules for `install.sh` (D11, D36)

- No existing `<target>/.claude/settings.json`: write the template as is.
- Existing file: deep-merge with `jq`.
  - `hooks.<event>`, on every event: first remove each hook whose command an earlier template wired and the payload no longer ships (`RETIRED_HOOK_COMMANDS` in `install.sh`: `spec-single-writer-guard.sh`, `tier-a-write-guard.sh`, `tier-b-write-guard.sh`). Then append each template command not yet present under that event, in the template's matcher group; a group the removal left empty under the same matcher takes the template group in its place, so the upgraded file reads as a fresh install's, and a group still empty goes. A command already present is not added again, so reinstalling is idempotent.
  - Matcher rule: an existing group that runs a template command under a matcher not covering the template's is resolved on its own, per group. A matcher covers the template's when its `|` alternatives include all of the template's, so a re-run asks nothing.
    - `merge`: union of both matchers' `|` alternatives in one group (`implementation|foo` with `implementation|integration` gives `implementation|foo|integration`). Offered only when both matchers are plain alternations (`[A-Za-z0-9_|]`).
    - `replace`: the group takes the template's matcher. A match-all template matcher makes merge and replace drop the matcher.
    - `keep`: the group stays as it is, with a line under Warnings.
    - At a terminal (stdin and stdout), the installer asks per group: it names the event and the scaffold command, shows the current, replace and merge matchers, and lists every hook in the group. Enter merges.
    - Without a terminal it never waits on input: it merges and prints a line under Warnings. A mixed group, one that also runs a non-template hook, is kept with a warning instead.
    - `--matchers=merge|replace|keep` sets the outcome for every group without asking, mixed groups included.
    - A match-all group (matcher absent, `""` or `"*"`) is never touched.
    - `--dry-run` asks nothing and shows the matcher changes the run would make: without `--matchers`, the no-terminal outcome. `--force` does not change matchers.
  - `permissions.allow` and `permissions.deny`: first remove each entry an earlier template wrote for a retired script or path (`RETIRED_PERMISSIONS` in `install.sh`: the three `regenerate-caches` script allows and `Edit(.workflow/cache/**)`, plus two older deny rules), then union with the template's, de-duplicated. Never remove other user entries.
  - Other `permissions` keys and unrelated top-level keys (`enabledPlugins`, `env`, ...): keep the user's values.
  - `outputStyle`: set it if absent. If the user set a different style, keep theirs and warn, or overwrite with `--force`.
  - `statusLine`: same rule as `outputStyle`. A project `statusLine` overrides a user-level one, so a user who prefers their own status line removes the key from the project settings.
- Any other conflicting scalar: refuse without `--force` (D11).
- Upgrades re-run the same merge. The scaffold does not track which entries it added, so a hook removed from the template must be removed from targets by hand (open: record scaffold-owned entries in the version stamp).
