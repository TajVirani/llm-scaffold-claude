# Fix plan: review escalation, wait time and spec worktrees

> Scaffold-only design doc (D30). Written 2026-11-01 from the review of specs 00010 to 00013 (`PLAN/workflow-review-00010-00013.md`). It records the decisions (D102–D112, copied into `assetlist.md` when built), the units that build them and which files each unit owns. The build runs outside `feature-workflow` at the stakeholder's request, as `PLAN/workflow-speed-fix.md` and `PLAN/test-cost-fix.md` did. Branch: `fix/workflow-review`.

## Why

The review measured four runs (one full path, three light path) after the D96–D101 fixes:

- Two questions that did not need asking stalled both sessions for about 80 minutes each while the stakeholder was away.
- Reviewers can only read code, so they report suspicions they cannot prove. Of 9 lens findings, 1 was a regression the change caused; the best catch of the four runs sat below the 80 cutoff and was saved only because the orchestrator probed it.
- Every side note became a backlog file, then a shelf file: about 600 lines of paperwork on 00010 for fixes under 30 lines of code.
- 8 of 11 extra mini-review launches were about comment wording.
- The full harness ran 4 to 8 times per spec on nearly identical trees.
- The spec branch is checked out in the main checkout, so two specs in parallel needed two full clones and hand-run fetches between them.

## Decisions

- **D102. Review findings are proven first, fixed by the worker when they touch the current work, and only escalated when they need the stakeholder.** (Amends D56, D96.) The stakeholder's rule, 2026-11-01. Every finding from any reviewer (implementer self-review, `profile-mini-review`, the Phase 4 lenses, `review-triage`) is checked by whoever raised it before it goes anywhere: a reproduction (the command and its output, or a failing test) or a quotable rule line. A finding nobody can prove is one line under `not_checked` and goes nowhere else: no ask, no file. A proven finding that affects the current work (on lines or files the spec changes, or inside its capabilities) goes back to the worker to fix: a fix round at 3.8, a rework at 4.7. The stakeholder is never asked about it. The stakeholder gets only three kinds of finding: **convoluted** (not simple to fix: it needs a lot of rework, or the fix may not behave the way the stakeholder expects, or it is hard to follow), **scope-expanding** (fixing it means doing more than the spec agreed), and **out of scope** (outside the spec's capabilities). Those are collected and asked in one batched question at the next existing ask, or at 5.5 at the latest, never as a standalone stop unless one is a blocker by the 00.22 rule. No new feature, requirement or refactor is ever filed from review on its own: for each out-of-scope or scope-expanding item the stakeholder chooses fold in (a scope change through the normal route), keep for later (one line on the spec's backlog list, D105) or drop.
- **D103. Reviewers may run code.** The four Phase 4 lenses and `profile-mini-review` may run commands in a scratch location (a throwaway worktree or `$TMPDIR`), never writing to the checkout or the task worktree. A `medium` or `high` finding needs a reproduction or a quotable rule line in `evidence`; without one it is a `not_checked` line. The 80 cutoff stays as a floor, not as the gate. `review-lessons` reads the spec's Assumptions and Non-goals; a gap the spec accepted scores 0.
- **D104. The implementer reviews its own diff before it stops.** Before its final toolchain run the implementation agent runs the comment lint (D106) and walks the work profile's Mini-review checklist and the readable-code lines against its own diff, fixes what it finds, and records `self_review` (item, verdict, note) in `implementation.yaml`. `check-task-result.sh` accepts the new field. The 3.7 mini-review still runs; it now starts from the self-review.
- **D105. Discovered work is one list per spec, not one file per item.** (Amends D96's filing.) A can-wait item the stakeholder keeps (D102) is one line in `.workflow/specs/work-backlog/<spec>.md`: problem, evidence, kind, status. Existing per-item files stay readable until they are closed. 5.9 asks one question over the list. No shelf file is written from review or sign-off unless the stakeholder asks for one.
- **D106. Comment wording is a lint, not a review round.** Build the comment-id lint from `.workflow/deferred/comment-id-lint.md` and mark the readable-code lines it covers `tool-covered` in the shell-scripts and test-harness profiles. Journey ids are allowed in a suite's `# Suite:` header, as 39 suites already have them, and nowhere else in body comments. When a 3.8 failure or a `low` triage patch is wording only, with the fix text in the note, the orchestrator applies the edit in the task worktree, commits it and launches the re-check (D98) instead of resuming the implementer.
- **D107. No stop for a question the workflow can answer itself.** The 0.6 "continue here or in a fresh session?" question is gone: the run continues, and a handoff is offered only when the session is genuinely long (two or more loop-backs), as a line in the progress report. The 3.14 suite-gap question is asked only the first time a project shows that gap; later specs append to the existing shelf file without asking. A `not_verifiable` host fact the orchestrator can settle with one command is settled at triage, not handed to the stakeholder.
- **D108. Toolchain results are reused more and re-run less.** `run-toolchain.sh` reuses a passing record when the `test` command string matches, whatever profile file named it, and the tree hash leaves out Tier A workflow files (`.workflow/capabilities.md`, `review-lessons.md`, `GLOSSARY.md`, `rules.md`, `decisions/`) unless the profile's commands changed. Sign-off skips the post-merge run when the merge result's tree equals a tree that already passed.
- **D109. Discovery spends less time before the first question.** Cache regeneration at 0.2.8 runs in the background beside retrieval, which reads the code for any stale cache as it already can, instead of retrieval waiting for publishing. The deeper-prompt confirmation and the 0.3.19 summary confirmation fold into the next ask when they would otherwise be their own round. When a decision adds a step to an ordered rule chain, "where in the order" is asked in the same round. The retrospective's candidate approval defaults to "nothing more" when 5.5 already said so. Phase 1 on a full-path spec that adds no new capability or harness lets implementers write the Phase 1 tests inside their tasks and runs 1.4 once on the merged wave.
- **D110. A small path for backlog-sized work.** Between trivial edit and light path: a request that already names the file, the cause and the test (a backlog item usually does) gets one questioning round, no library evaluation, one combined review agent (`review-combined`, with D103 execution rights) instead of three lenses, a short report, and the retrospective folded into the 5.5 ask. The light path also uses `review-combined`; the full path keeps the four lenses.
- **D111. A spec runs in its own worktree.** `workflow-paths.sh` gains `wf_project_root`, the top level of the checkout the caller runs in. Per-spec data uses it: `.step`, `artifacts/`, `commit-workflow-data.sh`, the spec-branch check, and agent worktrees under `.workflow/.worktrees/`. `wf_main_root` stays only where the main checkout is really meant: the session-start scan across worktrees. 1.1 and 0.3.20 create the spec branch in a new worktree off main instead of `git switch -c` in the main checkout. Task worktrees branch off the spec branch, light path included (`task/NNN-slug/T01-<slug>`, merged `--no-ff`), and are removed after their merge. Two specs can run in one clone.
- **D112. Merge routes are a setting, and merged branches are deleted.** When `origin` is not GitHub or GitLab, `task_review` reads as `local`, logged once, instead of printing "skipped" per task. Task PRs go into the spec branch and the spec PR into main when the remote is hosted; otherwise both are local merges after the stakeholder's go-ahead. 5.8 deletes the spec branch once it is merged (`git branch -d`), and 0.1.1 stops counting branches for the next spec number. Per-spec measurements (total time, waits, launches, harness runs, findings by class) go into the retrospective.
