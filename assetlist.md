# Workflow 2.0 Asset List

This list covers every skill, sub-agent, and hook that the decision flow needs before it can run. It is drawn from `PLAN/decision-flow.mermaid` (node IDs such as `0.2.4`) and `PLAN/decision-flow-reference.md` (section headings such as "Sub-agent task types", "Hooks" and "Processes outside the flow"). Each asset was checked against what already exists in `.agents/` and marked **New**, **Exists — reuse as-is**, or **Exists — needs changes**. "New (adapt from X)" means we write a new file and use an existing asset as its source. Where a plan step is done by the main session, a human, the host tool, or a plain command run, this list says so and does not create an asset for it. All assets go in `.agents/`, as `AGENTS.md` requires.

## Agents (sub-agent task types)

Each agent needs a launch prompt, which the plan asks for, and an entry in the `model-map/<task-type>.md` model map (D12). Definitions live in `.agents/agents/<name>.md` (D1) and may pin per-host models as `models: {claude: <alias>, codex: <model>}` (D35). The model is resolved by precedence: `agent-overrides.yaml`[type][host] > definition `models.<host>` > `model-map/<type>.md` [host] > none, which blocks at 00.14 (D35). The model map is separate project data (D2), resolved through `resolve-launch.sh` by the `pre-launch` hook, or by the orchestrator on Codex (D13, D33). "Receives" in the plan is the agent's whole context; the agent must not be given anything else.

### `retrieval`
- **Description:** Pulls the sections of Tier A, Tier B and `deferred/` that are relevant to the affected area, so the corpus never enters the main context.
- **Goals:** Return extracts only, each with its source path. Check `deferred/` in case this request is already on the shelf. Report cache stamps.
- **Triggers/inputs:** The affected area and the agreed terms.
- **Outputs/handoff:** Extracts written into `codebase-map.md`, along with `cache_stamps`. Consumed by gate 0.2.7 and by `discovery` and `questioning-loop`.
- **Plan reference:** 0.2.4; "Sub-agent task types"; design rule 3.
- **Status:** New.

### `library-evaluation`
- **Description:** Assesses third-party libraries and APIs for the affected concerns.
- **Goals:** Return options with cost, licence and fit.
- **Triggers/inputs:** The affected area and the external-systems section of `docs/rules.md`.
- **Outputs/handoff:** An options section in `codebase-map.md`.
- **Plan reference:** 0.2.5.
- **Status:** New.

### `cache-regeneration`
- **Description:** Derives one Tier B cache from code and stamps it.
- **Goals:** Regenerate the cache from scratch rather than patching the previous one. Output must be deterministic for a given scope and commit.
- **Triggers/inputs:** Scope (paths), cache type and the current commit. It never receives Tier A or the previous cache.
- **Outputs/handoff:** A cache file with frontmatter under `docs/cache/`. Feeds `codebase-map.md`.
- **Plan reference:** 0.2.8; `regen`.
- **Status:** New.

### `fact-lookup`
- **Description:** Answers a factual question from the code or docs, so the stakeholder is not asked it.
- **Goals:** Return the fact with its source, or "not determinable from the repo".
- **Triggers/inputs:** The question and the affected area. It never receives the stakeholder conversation.
- **Outputs/handoff:** Facts consumed by 0.3.11.
- **Plan reference:** 0.3.10.
- **Status:** New.

### `module-audit`
- **Description:** A deep read of the owning module, looking for reuse, gaps and constraints.
- **Goals:** Add findings to `codebase-map.md`. Never hand-edit caches; a wrong cache is a stamp problem.
- **Triggers/inputs:** The owning module's path and `codebase-map.md`. It never receives other modules.
- **Outputs/handoff:** Additions to `codebase-map.md`, consumed by 0.4.7.
- **Plan reference:** 0.4.6.
- **Status:** New. `codebase-design/SKILL.md` (with `DEEPENING.md`) supplies the module, interface and seam vocabulary. It replaced the older `improve-codebase-architecture/LANGUAGE.md`, which no longer exists.

### `implementation`
- **Description:** Writes a failing test, then the code, for one task in one module, under the injected profile.
- **Goals:**
  - Follow the TDD method written into its own prompt (D10).
  - Follow the profile's file locations, libraries and language rules; never choose its own.
  - Add negative and edge-case tests (3.4).
  - Fix whatever the tool output or mini-review names.
  - If the profile is wrong, report it and stop.
- **Triggers/inputs:** The task, the profile prepended to the launch prompt by the `pre-launch` hook (00.20, D33), the interfaces under test, and the relevant `codebase-map.md` extract. It never receives other tasks, other modules, the model map, or the rest of the spec folder.
- **Outputs/handoff:** A diff, test results, and any "profile is wrong" report. Consumed by `post-implementation-audit`.
- **Plan reference:** 3.3, 3.4 (also 1.2 and 1.3 under the `test-harness` and `e2e-browser` profiles).
- **Status:** New.

### `integration`
- **Description:** The single owner for shared-core changes, applied between batches.
- **Goals:** Apply core-change requests while conforming to the shared-core section of `docs/rules.md` and the profile.
- **Triggers/inputs:** Core-change requests, the work-type profile, and the shared-core section of `docs/rules.md`. It never receives individual task context.
- **Outputs/handoff:** A diff to core. Returns to the orchestrator.
- **Plan reference:** 3.2; gate 2.4.
- **Status:** New.

### `profile-mini-review`
- **Description:** Reviews one task's diff against only the profile checklist items that no tool can express.
- **Goals:** Pass, or list failed checklist items with their locations. Never re-lint or re-derive what the tool output already reports.
- **Triggers/inputs:** The diff, the profile's checklist section only, and the tool output from 3.5.
- **Outputs/handoff:** A pass or fail for gate 3.8. Recurring findings become input to 5.2.
- **Plan reference:** 3.7, 3.8.
- **Status:** New.

### `review-standards`
- **Description:** A Phase 4 lens covering standards, rules, profile and architecture conformance across the whole change.
- **Goals:**
  - Check against the Fowler smell baseline, boundary drift, intent violations of the placement ADR, and `GLOSSARY.md` naming.
  - Re-check the profiles with the whole change in view.
  - Do not re-lint.
- **Triggers/inputs:** The full diff, `docs/rules.md`, the profiles for the work types touched, the placement ADR, `GLOSSARY.md`, the documented standards, the Fowler baseline, and the 3.5 tool output. It never receives the other lenses' output or `spec.md`.
- **Outputs/handoff:** Findings with location and claimed consequence, sent to 4.4 triage.
- **Plan reference:** 4.1.
- **Status:** New (adapt from `code-review`). That skill's Standards sub-agent prompt and smell baseline are the source, but the new agent needs the added baselines and tool-output inputs.

### `review-end-state`
- **Description:** A Phase 4 lens that checks whether the change does what the spec says, and nothing it doesn't.
- **Goals:** Report what is missing, what was not asked for, and what is wrong. Use `artifacts/` as proof that the journeys ran.
- **Triggers/inputs:** The full diff, `spec.md`, `verification-plan.md` and `artifacts/`. It never receives standards or the other lenses' output.
- **Outputs/handoff:** Findings sent to 4.4.
- **Plan reference:** 4.2.
- **Status:** New (adapt from `code-review`). That skill's Spec sub-agent prompt maps closely to this lens.

### `review-targets`
- **Description:** A Phase 4 lens that measures the running build against the 1.1 targets.
- **Goals:** Report measured numbers against targets, with no judgement calls.
- **Triggers/inputs:** The running build and the targets.
- **Outputs/handoff:** Numbers sent to 4.4, and reported at 5.4.
- **Plan reference:** 4.3.
- **Status:** New.

### `standards-discovery`
- **Description:** A read-only brownfield scan that reports the conventions the code already follows, so `project-standards` ratifies them instead of inventing them (D80).
- **Goals:** Every observation carries file:line evidence; conventions are reported by frequency, mixed conventions are flagged, and each gets a proposed enforcement mechanism. Never interviews or writes.
- **Triggers/inputs:** `scope`, `work_types`, `instruction_files`, `since_commit` (refresh only) and an optional `focus`. Header optional (D31 as amended by D80).
- **Outputs/handoff:** Scope, Modules, Conventions, Versions, Contradictions, Unknowns and Discovered work sections, saved by `project-standards` under `.standards-staging/` and folded into its baseline.
- **Plan reference:** "Processes outside the flow" (Project setup); D80.
- **Status:** Implemented.

## Open questions / ambiguities

1. **Resolved (D5).** **Is `integration` a sub-agent?** It appears in the "Sub-agent task types" table, but 3.2 is not coloured purple in the diagram and is missing from the "ten launches" list and the ten dotted edges out of 00.15. That changes whether it needs a model-map entry and passes through the pre-launch hook.
2. **Resolved (D3).** **Phase-skill granularity.** The plan never names the skills that drive the main session. This list proposes one per phase, plus `feature-workflow` and `questioning-loop`. The alternative is a single `feature-workflow` skill with phase modules.
3. **Resolved (D4).** **Name collision on `cache-regeneration`.** The plan uses the same name for both the external skill and the sub-agent task type. Should the skill be renamed (for example, `regenerate-caches`)?
4. **Resolved (D1, D2; model-map path → D12).** **Two meanings of `agents/`.** The plan's `agents/<task-type>.md` is a model-selection map at the repo root. Agent definitions would presumably also live under `.agents/` (for example, `.agents/agents/`), and Claude Code expects `.claude/agents/`. We need to decide the paths and the shim symlink, and whether the model map should instead live in the agent definition frontmatter (`model:`).
5. **Resolved (→ D16).** **Where does the single-writer guard get the "current workflow step"?** `spec-single-writer-guard` and `tier-a-write-guard` both need it, but no state file or marker is defined. We need a workflow-state mechanism, perhaps written by `status-transition`. This is still open. D7 makes `status-transition.sh` a script, which could write the marker too.
6. **Resolved (D7).** **Is `status-transition` really a hook?** "At each node that changes state" is not a host event. It may be better as a helper script that the phase skills call, with the guard hook allowing only that script.
7. **Resolved (D7): it is a script that `discovery` calls.** **Event for `cache-stamp-check`.** "Before retrieval reads any file under `docs/cache/`" could be a PreToolUse on the `retrieval` launch, or a check inside the retrieval prompt. A sub-agent's own Read calls may not be hookable in the same way.
8. **Resolved (→ D13, D14).** **Where the profile hook finds `work_type`.** The hook reads it from `tasks.md`, so the launch request must carry the task ID. A launch-request convention is needed for both pre-launch hooks, including declaring whether the sub-agent will launch sub-agents of its own (00.15).
9. **Resolved (→ D10).** **Missing source skills.** The plan says local copies of Matt Pocock's *domain-modeling*, *wayfinder* and *codebase-design* are in the project, but none are vendored. Only `grill-with-docs`, which references `domain-modeling`, and `improve-codebase-architecture` (`LANGUAGE.md`) contain fragments. Should we vendor them or re-derive them?
10. **Resolved (→ D24).** **Deferred handoff and archival (0.3.17, 4.8, 00.9).** These are treated here as steps inside `questioning-loop`, `review-triage` and `discovery`, using a shared template. Should they be a small shared `deferred-handoff` skill instead?
11. **Resolved (→ D25).** **Retrospective (5.7).** It is folded into `sign-off` here. BMad treats it as its own skill, so it could be split out.
12. **Resolved (→ D26).** **Test profiles.** 1.2 and 1.3 need `test-harness` and `e2e-browser` profiles created by project setup. These are project data, not scaffold assets, but should the scaffold ship example profiles?
13. **Resolved (→ D9).** **Host portability.** Every hook is specified in Claude Code event terms. The plan does not say how agents that are not Claude Code get model selection, profile injection or write guards, even though `.agents/` is meant to be agent-agnostic.
14. **Resolved (→ D27).** **Commands.** The plan requires no commands. Should the phase skills also be exposed as slash commands (for example, `/feature`), or is invoking them as skills enough?
